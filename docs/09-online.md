# 09 · 联网对战（M2）

> 目标：真人对真人的段位赛。人不够时用 AI 补满 6 人桌。服务器是唯一的权威，客户端只负责演出。
> 关联文档：[01 市场调研](01-market-research.md)（地区和合规）· [02 产品范围与技术选型](02-product-and-tech.md) · [06 心理战](06-mind-games.md) · [08 演出](08-presentation.md)

## 1. 架构

```
浏览器（PixiJS 演出）  ──WebSocket /ws──▶  游戏服务器（Node.js）
   与单机共用牌桌、导演、演出代码              ├─ 规则引擎：同一份 C++ 编译成的 WebAssembly
                                              ├─ 匹配：每种赛制一个队列，倒计时结束 AI 补位
                                              ├─ 牌桌：实时推进，等每位玩家的动画播完再继续
                                              └─ SQLite：游客账号、段位分、对局记录
```

- **同一份规则代码**：服务器跑的是客户端里那份 C++ 引擎编译成的 WebAssembly，两边永远不会出现"规则不一致"。
- **服务器说了算**：发牌、下注合法性、行动计时、结算都在服务器上。客户端只收到自己应该看到的东西（自己的底牌、公开的事件），看不到别人的牌，也没法伪造别人的操作。
- **座位旋转**：每个玩家看到的自己都在 0 号座（第一人称牌桌的位置）。服务器给每个人发事件时，把座位号转成那个人的视角，所以单机和联网用的是同一套牌桌和演出代码。
- **AI 补位**：开桌时空位由 AI 坐上，用的是单机里那 6 种性格。AI 只看得到自己的牌，和真人一样通过公开信息读人（台词、下注快慢和大小、亮出的牌）。
- **其他真人**：用 AI 没占用的角色形象，名牌上是玩家昵称。系统不会替真人说台词、发表情。

## 2. 一局的节奏

| 环节 | 规则 |
|---|---|
| 匹配 | 第一个人进队列后开始倒计时（默认 20 秒）；凑满 6 人或时间到就开桌，空位 AI 补上。难度按这桌玩家的平均段位分：600 分（黄金）以上用困难 AI |
| 动画同步 | 服务器每推送一批事件，就等所有在线玩家回复"播完了"再继续，最多等 10 秒（防止一个卡顿的客户端拖住整桌） |
| AI 思考 | 和单机一样有思考时间（这也是 AI 的"破绽"之一），期间所有人看到它的思考计时 |
| 行动计时 | 每次行动 20 秒，加上整局共用的 30 秒时间银行。超时自动过牌，不能过牌就弃牌 |
| 心理战 | 台词、表情、动作随时可以发，服务器限频（每条街台词 3 句、表情 4 个、动作 3 个、表情包 3 个），立刻推送给全桌 |
| 亮牌 | 没人跟注赢下底池的玩家有 5 秒决定亮不亮 |
| 手与手之间 | 停 4 秒 |
| 结算 | 段位分按名次：60 / 30 / 10 / 0 / −15 / −30，并列取平均，最低 0 分 |

## 3. 断线、离开、重连

- **断线**：座位保留，行动计时照常走。在计时内连回来就能接着打；超时就自动过牌或弃牌。
- **重连**：客户端自动重连（同一个账号令牌）。服务器把这一手从头的事件发回来，客户端瞬间重放、追上进度；如果正轮到你，会重新发行动请求（剩余时间扣掉断线期间）。
- **主动离开**：剩下的手牌自动过牌或弃牌，段位分照常在这局结束时结算。
- **整桌没人看**：所有真人都离开或断线超过 1 分钟，剩下的部分不再停顿，直接打完、记录结果。
- **页面在后台**：浏览器会暂停后台页面的动画，所以后台时客户端直接跳过动画、马上回复"播完了"，不拖慢别人。

## 4. 协议

一条 WebSocket，消息都是 JSON。类型定义在 [`web/src/net/protocol.ts`](../web/src/net/protocol.ts)，客户端和服务器共用。

| 方向 | 消息 |
|---|---|
| 客户端 → 服务器 | `hello`（版本、昵称、令牌）· `queue` / `cancel` · `act` · `signal` · `show` · `ready`（这批事件播完了）· `leave` · `ping` |
| 服务器 → 客户端 | `welcome`（令牌、段位分）· `queue`（已找到几人、还剩几秒）· `matched`（座位表）· `events`（按顺序播放，播完回 `ready`）· `live`（台词等，立刻显示）· `turn`（谁在思考）· `ask`（轮到你）· `askShow` · `pause` · `end`（名次和段位分变化）· `refused` · `error` |

引擎这边，`poker::app::Session` 增加了"多个真人座位"：构造时传入真人座位的掩码，`signalFrom(seat, …)`、`show(seat, mask)`、`drainAll()`（每个事件带上谁能看到）、`stateFor(seat)`。单机用的老接口保持不变。

## 5. 服务器推荐

**首发市场是日本（见 [01](01-market-research.md) 第 2 节），所以服务器放在东京。**

| | 推荐 | 说明 |
|---|---|---|
| 现在（测试和小规模公测） | **AWS Lightsail 东京**，2 核 4 GB，约 $20/月 | 固定 IP、按月计费、控制台简单；以后要扩容可以直接迁到 AWS 的其他服务 |
| 备选 | Vultr 东京同配置，约 $20/月 | 价格相近，按小时计费 |
| 域名和 HTTPS | 任意域名注册商 + Caddy 自动申请证书 | 已经写好配置，见第 6 节 |

扑克是回合制，延迟 50–150 毫秒完全够用；东京到日本本地约 10–30 毫秒，到港澳台、东南亚一般也在 100 毫秒以内。

**不考虑中国大陆机房**：大陆不是目标市场（棋牌类版号基本不发），也就不需要 ICP 备案。

**容量**：一张桌子的计算量很小（主要是 AI 的胜率估算），单个 Node 进程预计能同时跑上百张桌。正式公测前要做一次压测（`server/tools/smoke.ts` 可以改成批量机器人）。以后要横向扩展时，把匹配队列放进 Redis，每个进程负责一部分牌桌。

## 6. 部署

仓库根目录有 `Dockerfile`，`deploy/` 里有 Docker Compose 和 Caddy 配置。

```bash
# 在服务器上（装好 Docker）
git clone <仓库> poker && cd poker/deploy
DOMAIN=poker.example.com docker compose up -d --build
# 浏览器打开 https://poker.example.com
```

- 游戏服务器同时提供网页客户端（`/`）和 WebSocket（`/ws`），Caddy 负责 HTTPS 并转发。
- 数据在 Docker 卷 `pokerdata` 里的 `/data/poker.db`（SQLite），要定期备份。
- 健康检查：`/healthz` 返回在线人数、牌桌数、排队人数。
- 环境变量：`MATCH_WAIT_SEC`（匹配等待秒数，默认 20）、`PORT`、`DB_FILE`、`STATIC_DIR`。

## 7. 本地开发

```bash
cd server && npm install && MATCH_WAIT_SEC=5 npm start      # 游戏服务器，:8787（Node 22.18+）
cd web && npm run dev                                       # 客户端，:5173，自动连 :8787
node server/tools/smoke.ts 3                                # 3 个脚本玩家打一整局，检查结果
```

客户端连接的服务器地址：`?server=wss://…` 参数优先；在 vite 的 5173、4173 端口时连本机 8787；否则连当前网址的 `/ws`。连不上服务器时（比如 claude.ai 上的试玩页面），段位赛会提示改打离线段位赛。

## 8. 还没做的（按优先级）

1. **正式账号**：现在是游客账号（令牌存在浏览器里，换设备就是新号）。日本市场优先接 Apple、Google、X 登录，之后再接 Steam。
2. **防作弊**：多开串通检测（同 IP、同设备在一桌）、异常胜率监控；段位赛禁止同一设备的两个号同桌。
3. **段位赛规则细化**：段位保护、赛季重置、按段位分匹配（现在是谁先来谁同桌）。
4. **观战和牌谱**：服务器已经存了每局结果，下一步存完整事件流，就能做牌谱回放。
5. **好友房和语音**。
