# 02 · 产品范围与技术选型

## 1. 核心循环（MVP 只验证这一件事）

```
匹配（或 AI 补位）→ 6 人同桌 → 18 手快速赛 / 30 手标准赛 → 按名次结算段位分 → 再来一局
```

**MVP 的唯一问题：这个循环打起来，是不是比 Poker Chase 更爽、更想再来一局？**
其他系统（抽卡、剧情、公会、活动）全部等这个问题有了肯定答案再说。

## 2. 里程碑

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M0 规则内核**（本次提交 ✅） | C++ 规则引擎（牌型、下注、边池、锦标赛）、AI、命令行试玩、模拟器、单元测试 | 测试全过；模拟器能跑出赛制数据 |
| **M1 单机可玩原型**（进行中：网页版可玩 ✅） | 网页客户端：牌桌、6 个座位、角色头像和切入图（目前是占位图）、0 到 4 级演出、和 AI 打三种赛制 | 找 10 到 20 人试玩，"想再来一局"的比例 |
| **M2 联机封测** | C++ 权威服务器、匹配（休闲场可以用 AI 补位，段位场不行）、账号、段位、牌谱 | 小规模封测：留存、单局时长、掉线率 |
| **M3 角色与商业化** | 6 到 8 名角色、好感度、外观商店、主要角色的 Live2D、委托画师绘制正式立绘 | 付费意愿测试 |

**明确不在 MVP 里：** 世界观和剧情、抽卡、公会、活动、自由文字聊天。

> 不做自由聊天：德扑里自由聊天容易出现"报牌"串通和骂人。只提供表情和固定短语（和雀魂一样）。

## 3. 技术选型

> **决定（2026-10）：网页优先。** C++ 规则内核编译成 WebAssembly，界面用 TypeScript + PixiJS。最初推荐的 Godot 4 改为备选。

### 3.1 总体架构

```
            ┌──────────────── poker_core (C++20, 零依赖) ────────────────┐
            │  牌型判定 · 下注状态机 · 边池 · 锦标赛 · 确定性 RNG · 事件流   │
            └──────▲──────────────────▲─────────────────────▲──────────┘
                   │                  │                     │
        ┌──────────┴───┐   ┌──────────┴────────────┐  ┌─────┴──────────┐
        │ 游戏服务器      │   │ 网页客户端              │  │ 工具             │
        │ C++ (M2)      │   │ C++ → WebAssembly      │  │ CLI / 模拟器 /    │
        │ 权威判定        │   │ + TypeScript + PixiJS  │  │ 牌谱回放 / AI 训练 │
        └──────────────┘   └───────────────────────┘  └────────────────┘
```

**关键原则：**
- **同一份规则代码**跑在服务器、网页单机模式（WebAssembly）、AI 模拟和牌谱回放里，规则永远不会"两边不一致"。
- **服务器说了算**：联机时洗牌、发牌、结算都在服务器；客户端只收到自己座位能看到的事件（引擎里的 `PlayerView` 和 `Event.visibleTo` 已经实现了这个隔离）。
- **确定性**：同一个种子加同一串操作，结果完全一样。牌谱回放、bug 复现（网页版支持 `?seed=`）、可验证洗牌都基于这一点。

### 3.2 客户端：为什么选网页（WebAssembly + PixiJS）

| 方案 | 结论 | 理由 |
|---|---|---|
| **C++ → WebAssembly + TypeScript + PixiJS** | ✅ **采用** | 雀魂本身就是网页游戏（Steam 版也是网页套壳），路线已被验证；试玩时**发个链接就能玩**，M1 收集反馈最快；Live2D 有**官方**网页 SDK（Cubism SDK for Web）；C++ 内核原样复用 |
| Godot 4 + C++ GDExtension | 备选 | 一套工程导出所有平台，但网页端接入 C++ 扩展要额外配置、坑多；Godot 的 Live2D 只有社区插件 |
| Unity | 不采用 | 不是 C++；网页导出包体大、启动慢 |

**各平台怎么上：**
- **网页**：直接部署静态文件（任何静态托管或 CDN）
- **Steam / PC**：用 Electron 或 Tauri 套壳（雀魂的做法）
- **手机**：先用浏览器玩；要上应用商店时用 Capacitor 套壳，或者再评估原生方案

**网页客户端的结构**（`web/`）：

| 层 | 技术 | 职责 |
|---|---|---|
| 引擎 | `poker.js`（Emscripten 生成，.wasm 内联） | 规则、AI，通过 `poker::app::Session` 用 JSON 交换事件和状态 |
| 导演 | `director.ts` | 按顺序消费引擎事件，转成动画，控制 AI 行动节奏 |
| 牌桌 | PixiJS（WebGL） | 牌桌、座位、牌、筹码、演出特效 |
| 界面 | HTML + CSS 覆盖层 | 菜单、HUD、操作区、结算。和画布共用 1920×1080 设计坐标，一起缩放 |

**不需要安装 Emscripten 也能开发前端**：生成好的 `web/src/wasm/poker.js` 提交在仓库里；只有改了 C++ 才需要运行 `scripts/build-wasm.sh` 重新生成。

### 3.3 服务器（M2）

- C++20，和客户端共用 `poker_core`
- 网络：WebSocket（例如 uWebSockets 或 Boost.Beast），消息格式用 Protobuf 或 FlatBuffers
- 每张桌子是一个单线程 actor，一个进程托管成百上千张桌子（德扑计算量很小）
- 存储：PostgreSQL（账号、段位、牌谱），Redis（匹配队列、在线状态）
- 随机数：服务器用 CSPRNG（实现 `poker::Rng` 接口即可接入），之后做**可验证洗牌**：开局公布种子哈希，局后公开种子
- 反作弊：手牌只发给本人；段位赛随机匹配、不能组队；后期做合谋检测（统计异常放水和弃牌模式）

### 3.4 本仓库结构

```
core/      规则引擎（poker_core）：card, rng/deck, hand_eval, pot, hand, tournament
ai/        单机 AI（poker_ai）：蒙特卡洛胜率 + 性格化启发式策略
app/       单机对局会话（poker_session）：网页客户端调用的接口
tools/cli  命令行试玩：你 vs 5 个 AI
tools/sim  模拟器：赛制时长、技术体现程度、AI 强度
tests/     单元测试（无第三方依赖）
web/       网页客户端（TypeScript + PixiJS + Vite）；web/wasm 是 WebAssembly 绑定
scripts/   build-wasm.sh：把 C++ 编译成 web/src/wasm/poker.js
docs/      设计文档
```
