# 02 · 产品范围与技术选型

## 1. 核心循环（MVP 只验证这一件事）

```
匹配（或 AI 补位）→ 6 人同桌 → 18 手快速赛 / 30 手标准赛 → 按名次结算段位分 → 再来一局
```

**MVP 的唯一问题：这个循环打起来，是不是比 Poker Chase 更爽、更想再来一局？**
其他系统（抽卡、剧情、公会、活动）全部等这个问题有了肯定答案再说。

## 2. 里程碑

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M0 规则内核**（本次提交 ✅） | C++ 规则引擎（牌型、下注、边池、锦标赛）、AI、命令行试玩、模拟器、单元测试 | 测试全过；模拟器能跑出赛制数据 |
| **M1 单机可玩原型** | Godot 客户端：牌桌、6 个座位、AI 美术的角色头像和切入图、0 到 3 级演出、和 AI 打快速赛 | 找 10 到 20 人试玩，"想再来一局"的比例 |
| **M2 联机封测** | C++ 权威服务器、匹配（休闲场可以用 AI 补位，段位场不行）、账号、段位、牌谱 | 小规模封测：留存、单局时长、掉线率 |
| **M3 角色与商业化** | 6 到 8 名角色、好感度、外观商店、主要角色的 Live2D、委托画师绘制正式立绘 | 付费意愿测试 |

**明确不在 MVP 里：** 世界观和剧情、抽卡、公会、活动、自由文字聊天。

> 不做自由聊天：德扑里自由聊天容易出现"报牌"串通和骂人。只提供表情和固定短语（和雀魂一样）。

## 3. 技术选型

### 3.1 总体架构

```
            ┌──────────────── poker_core (C++20, 零依赖) ────────────────┐
            │  牌型判定 · 下注状态机 · 边池 · 锦标赛 · 确定性 RNG · 事件流   │
            └────────────▲──────────────────▲─────────────────▲─────────┘
                         │                  │                 │
              ┌──────────┴───┐    ┌─────────┴────────┐  ┌─────┴──────────┐
              │ 游戏服务器      │    │ 客户端 (Godot 4)   │  │ 工具             │
              │ C++ (M2)      │    │ GDExtension 链接   │  │ CLI / 模拟器 /    │
              │ 权威判定        │    │ 单机模式直接跑内核   │  │ 牌谱回放 / AI 训练 │
              └──────────────┘    └──────────────────┘  └────────────────┘
```

**关键原则：**
- **同一份规则代码**跑在服务器、客户端单机模式、AI 模拟和牌谱回放里，规则永远不会"两边不一致"。
- **服务器说了算**：联机时洗牌、发牌、结算都在服务器；客户端只收到自己座位能看到的事件（引擎里的 `PlayerView` 和 `Event.visibleTo` 已经实现了这个隔离）。
- **确定性**：同一个种子加同一串操作，结果完全一样。牌谱回放、bug 复现、可验证洗牌都基于这一点。

### 3.2 客户端引擎：推荐 Godot 4 + C++ GDExtension

你喜欢 C++，这是选择的出发点。

| 方案 | 语言 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **Godot 4** | 内核 C++（GDExtension），界面 GDScript | MIT 开源、**无分成**；2D 能力强；一套代码导出 Windows / Mac / Linux / Android / iOS / Web；C++ 内核可以直接链接进去 | Live2D 只有社区插件（[gd_cubism](https://oosmetrics.com/repo/MizunagiKB/gd_cubism)，C++ 写的，约 270 星）；日本商业项目案例少 | ✅ **首选** |
| Unity | C# | 日本手游的事实标准；Live2D **官方** SDK；招人容易 | 不是 C++（内核只能做成原生插件接入）；授权政策有过反复 | 备选 |
| axmol（cocos2d-x 社区分支） | C++ | 纯 C++，2D 手游起家 | 社区小，工具链和编辑器弱 | 不推荐 |
| Unreal | C++ | 3D 顶级 | 对 2D 卡牌游戏太重，包体大 | 不推荐 |

**为什么 Godot 风险可控：**
1. 规则内核与引擎**完全解耦**。哪天真要换 Unity，内核编成原生插件照样用，损失的只有界面层。
2. MVP 阶段**不需要 Live2D**：用静态立绘加 Godot 的补间和着色器做呼吸、眨眼、晃动就够了。到 M3 再评估 gd_cubism 或 Spine（Spine 有官方 Godot 运行库）。
3. 界面用 GDScript 写，迭代快；性能敏感的部分（AI 胜率模拟）在 C++ 里。

### 3.3 服务器（M2）

- C++20，和客户端共用 `poker_core`
- 网络：WebSocket（例如 uWebSockets 或 Boost.Beast），消息格式用 Protobuf 或 FlatBuffers
- 每张桌子是一个单线程 actor，一个进程托管成百上千张桌子（德扑计算量很小）
- 存储：PostgreSQL（账号、段位、牌谱），Redis（匹配队列、在线状态）
- 随机数：服务器用 CSPRNG（实现 `poker::Rng` 接口即可接入），之后做**可验证洗牌**：开局公布种子哈希，局后公开种子
- 反作弊：手牌只发给本人；段位赛随机匹配、不能组队；后期做合谋检测（统计异常放水和弃牌模式）

### 3.4 本仓库结构

```
core/      规则引擎（poker_core）：card, rng/deck, hand_eval, pot, hand, tournament
ai/        单机 AI（poker_ai）：蒙特卡洛胜率 + 性格化启发式策略
tools/cli  命令行试玩：你 vs 5 个 AI
tools/sim  模拟器：赛制时长、技术体现程度、AI 强度
tests/     单元测试（无第三方依赖）
docs/      设计文档
```
